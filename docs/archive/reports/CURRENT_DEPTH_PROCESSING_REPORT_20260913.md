# 当前水下双目深度处理报告（2026-09-13）

## 1. 本次处理的最终口径

本项目当前明确采用以下工程口径：

1. `Calibration/zed_custom_opencv.yml` 是当前处理流程唯一使用的相机标定文件。
2. SVO 内嵌的原生 ZED 标定不参与本次最终深度视频生成。
3. 深度计算引擎采用 ZED SDK `MEASURE.DEPTH` / `DEPTH_MODE.NEURAL`，不是只能使用独立 OpenCV SGBM。
4. SDK 在 `open()` 时显式传入 Custom 标定，并关闭 SDK 自标定，避免 SDK 回退或混入 SVO 内嵌标定。
5. 输入 SVO 从第 0 帧开始连续回放到最后一帧，共处理全部 `35,855` 帧，不是抽样的 20 帧、100 帧或 1,000 帧。
6. 最终视频放在项目根目录，不放在 `output/` 目录。

独立 SGBM 仍然保留为诊断和交叉检查工具：它能验证“原始图像 → Custom 几何校正 → disparity → 深度”的几何链路，但本次最终交付的视频采用 SDK 深度引擎，以满足“使用 ZED SDK 导出 depth map”的要求。

## 4. SDK 流程的具体设置

最终视频由 `convert_zed_custom_depth_to_video.py` 生成。关键设置如下：

```text
depth_mode                    = NEURAL
depth_source                  = pyzed.sl.MEASURE.DEPTH
optional_opencv_calibration   = Calibration/zed_custom_opencv.yml
camera_disable_self_calib     = True
coordinate_units              = METER
measure3D_reference_frame     = CAMERA
confidence_threshold          = 30
texture_confidence_threshold  = 100
depth_stabilization            = 0
image_enhancement              = False
```

其中最重要的是：

```python
init.optional_opencv_calibration_file = str(calibration_path)
init.camera_disable_self_calib = True
```

因此，本次流程不是“读取原生 `VIEW.LEFT/RIGHT` 后再假装使用 Custom 参数”，也不是“读取原生 SDK depth 后再乘一个比例”。SDK 在打开 SVO 时就被要求使用指定的 Custom OpenCV 标定文件。

## 5. 视频可视化规则

最终视频中的颜色只是深度图的可视化，不改变原始深度数值：

| 项目 | 设置 |
|---|---|
| 色图 | OpenCV `TURBO` |
| 蓝色 | Near，近处 |
| 红色 | Far，远处 |
| 黑色 | 无效深度 |
| 固定显示范围 | `1.5–3.5 m` |
| 超出显示范围的有效值 | 颜色裁剪到蓝端或红端，不丢弃深度值 |
| 输出尺寸 | `1920 × 1080` |
| 输出帧率 | `30 FPS` |
| 编码 | `mp4v` |

固定全局色阶是为了让不同帧之间可比较。它不是逐帧自动拉伸，因此某一帧的红/蓝颜色含义不会因为该帧自己的最小值和最大值改变。

## 9. 关于“中心应该比边缘近”的核查结论

当前必须区分三个层面：

1. **颜色方向**：已确认 `TURBO` 的低值为蓝、高值为红，因此“蓝=近、红=远”的标注没有写反。
2. **标定路径**：最终视频确实使用 Custom 标定，不使用原生 SVO 标定；因此不能再把当前视频出现的中心/边缘关系归因于误用了 native `fx`。
3. **场景几何与匹配质量**：中心比边缘近是很多前视场景中的合理经验，但不是所有帧、所有像素都必须满足的数学约束。目标可能倾斜，边缘可能确实存在更近物体；弱纹理、反光、重复纹理和边缘遮挡也会造成深度无效或错误。

前期独立 SGBM 诊断显示：

- Custom `alpha=0` 流程在前段可靠帧中明显减弱了 native 的“中心远、边缘近”趋势；
- 100 帧左右一致性检查中，LR 有效率不低于 10% 的帧里，大多数满足中心深度小于边缘深度；
- 后段帧的 LR 有效匹配率显著下降，后段少量“边缘更近”不能作为全局标定错误的充分证据；
- `alpha=0` 的 rectified 虚拟主点约为 `(1212.686, 532.640)`，并不等于图像坐标中心 `(960,540)`，所以“中心/边缘”比较还混入了投影中心选择问题。

因此，当前最稳妥的表述是：Custom 标定已经被严格用于最终 SDK 视频；前段数据支持其比 native 标定更符合当前水下图像趋势，但仅凭视频颜色和中心/边缘观察，仍不能证明所有像素的绝对水下距离都已得到独立真值验证。

## 10. 为什么没有统一乘 1.333

水下折射模型中 `1.333 × fB/d` 可以作为某些空气标定/平面防水罩假设下的候选近轴修正，但本项目当前缺少：

- 相机光心到平面防水罩的距离；
- 玻璃厚度和玻璃折射率；
- 标定是在空气中还是在水中完成的可追溯记录；
- 已知水下距离的独立真值目标。

如果 `Calibration/` 本身就是同一防水罩和同一水下条件下的等效标定，再乘 `1.333` 很可能重复补偿。故最终 SDK 视频保留 SDK 根据 Custom 标定得到的深度，不额外乘折射率。绝对尺度仍应通过已知距离目标做最终验证。

## 11. SDK Custom 中心与边缘区域的实测比较

为直接回答“中心是否比多数边缘区域更近”，使用同一套 `MEASURE.DEPTH + NEURAL + zed_custom_opencv.yml`，从完整 SVO 均匀抽取 100 个位置。每帧将深度图划分为等大小的 `3×3` 网格，中间网格定义为中心区域，周围 8 个网格定义为边缘区域。原始结果保存在 `CUSTOM_SDK_CENTER_EDGE_100.json`。

结果如下：

| 比较对象 | 中位数 |
|---|---:|
| 精确中心像素 `(960,540)` | `2.2012 m` |
| 中心 `1/3×1/3` 区域 | `2.2047 m` |
| 8 个边缘区域中位数的合并统计 | `2.2013 m` |

按每一帧的精确中心像素与 8 个边缘区域逐一比较：

- 99 帧中心像素有效；
- 只有 `13/99` 帧（`13.1%`）满足“中心比多数有效边缘区域更近”；
- 因此，当前 SDK Custom depth 数据**不能说中心比多数边缘区域更近**；整体上中心与边缘非常接近，中心甚至略微比边缘合并中位数更远约 `3 mm`。

方向上存在明显的不对称：

| 边缘区域 | 中心更近的帧比例 | 边缘深度 − 中心深度中位数 |
|---|---:|---:|
| 左上 | `2.0%` | `-0.090 m` |
| 上 | `49.5%` | `-0.0003 m` |
| 右上 | `99.0%` | `+0.0746 m` |
| 左 | `1.0%` | `-0.0963 m` |
| 右 | `97.0%` | `+0.0745 m` |
| 左下 | `1.0%` | `-0.1098 m` |
| 下 | `40.4%` | `-0.0036 m` |
| 右下 | `94.9%` | `+0.0735 m` |

也就是说，当前结果表现为“右侧大部分区域比中心更远、左侧大部分区域比中心更近”，而不是以中心为对称轴的“中心近、四周远”。这更像是场景平面姿态、相机姿态/视线方向、有效投影主点偏移或左右区域匹配质量共同造成的方向性梯度；仅凭这一统计不能单独证明是畸变没有校正。它也说明，在判断 Custom 标定时，不能把所有边缘区域简单合并成一个“远处背景”。

该分析脚本为 [`analyze_custom_sdk_center_edge.py`](analyze_custom_sdk_center_edge.py)。
